# Microservice Decomposition (research lane)

This is a parallel research lane that decomposes the Spring Boot
backend into independently deployable microservices. It is governed
by `.kiro/specs/microservice-decomposition/`. The monolith spec at
`.kiro/specs/spring-boot-backend-migration/` is the authoritative
production baseline.

> Nothing in this directory should be deployed to the family's real
> data. It is a research artefact for learning distributed-systems
> patterns.

## Layout

```

  service-common/         Shared infrastructure (kernel, outbox relay, saga
                          orchestrator, RabbitMQ topology, request-id
                          filter, global error handler, observability,
                          mTLS, JSON helpers, contract envelopes)
  identity-service/       Phase 1.1
  audit-service/          Phase 1.2
  tree-service/           Phase 2.1 (orchestrator)
  members-service/        Phase 2.2 (orchestrator)
  relationships-service/  Phase 2.3 (orchestrator)
  events-service/         Phase 2.4 (orchestrator)
  media-metadata-service/ Phase 2.5 (orchestrator)
  binary-storage-service/ Phase 3.1
  sharing-service/        Phase 4.1
  reporting-service/      Phase 4.2
  transfer-service/       Phase 5.1 (orchestrator)
  gateway-service/        Phase 1.3 (Spring Cloud Gateway)

infra/
  docker-compose.yml      MySQL 8.4 + RabbitMQ + Prometheus + Grafana + 12 services
  mysql/init/             Per-service schemas + per-service MySQL users
                          (including SELECT-only cross-service grants)
  prometheus/             Scrape config + alert rules
  grafana/                Provisioning for datasource + dashboards
  ca/                     Local CA for mTLS (git-ignored, generated by `make ca`)
  schemas/                Event schemas (JSON Schema registry)
  seed/                   Import seed workflow

docs/microservice/        Research deliverables
  adr/101..105            ADR documents
  notes.md                Running journal (post-migration strategy)
  comparison.md           Monolith vs. microservice trade-off matrix
  blog.md                 Lessons-learned write-up
  security.md             Security baseline (Phase 6.4)
  observability.md        Tracing / metrics / alerts
  sagas/README.md         Saga inventory + runbooks
  runbooks/local-dev.md   Local-dev runbook

tools/
  ca/                     make-ca.sh + rotate-cert.sh
  bench/                  Workload benchmark (Phase 7.1)
  codegen/                V1__outbox.sql + V2__saga_log.sql templates

Makefile                  Convenience targets (make up, make build-all, make bench, ...)
```

## Migration strategy

Each `services/<svc>/` module owns the relevant subset of the monolith
domain. Source code is **copied** from the original backend modules
and re-packaged under `vn.giapha.research.<svc>` (non-hyphenated). The
monolith is now fully migrated; the `backend/` directory has been
removed.

Each service:
- Has its own `pom.xml` (depends on `service-common`).
- Has its own `application.yml` (database, RabbitMQ host, Flyway schema).
- Has its own `Dockerfile`.
- Has its own Flyway migrations under `db/migration/`.
- Uses its own MySQL user (no shared service account).

## Build and run

```bash
cp .env.example .env
make build-all       # mvn -DskipTests package on all services
make up              # docker compose up
```

See `docs/microservice/runbooks/local-dev.md` for the full local-dev
walkthrough.

## Phases

- Phase 0 — Foundation (infra, libs, outbox, clock)
- Phase 1 — Identity, audit, gateway
- Phase 2 — Tree content decomposition (ADR-101 strategy B)
- Phase 3 — Binary pipeline
- Phase 4 — Sharing and reporting
- Phase 5 — Transfer
- Phase 6 — Cross-cutting (sagas, reconciliation, observability, security)
- Phase 7 — Research deliverables (bench, comparison, blog, notes)

See `.kiro/specs/microservice-decomposition/tasks.md` for the full
task list and `docs/microservice/notes.md` for the running journal.
