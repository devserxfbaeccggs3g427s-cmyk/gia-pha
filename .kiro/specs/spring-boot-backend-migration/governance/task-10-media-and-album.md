# Task 10 — Implement Media & Album Service and Blob controls

## Scope

Media & Album Service owns media/album metadata, associations, upload
intents, quarantine, verification, mandatory scanning, thumbnails,
tombstones, retention, cleanup, and binary replication
(`requirements.md:108`, `design.md:71,166,194`). The service is the
owning service for the media activation Saga (`design.md:149`).

The official-JS Blob Control Gateway is the only path for browser
data-plane uploads to private quarantine. Capabilities are bearer
secrets and MUST NEVER appear in events, logs, or domain tables.

## Domain ownership

| Aggregate | Authoritative writes |
|---|---|
| `media_asset` | Media service only. Tombstones never delete the row; they set `status='TOMBSTONED'` and `tombstoned_at`. |
| `album` | Media service only. |
| `media_quarantine` | Media service only. Created when an upload intent is opened; updated by the scanner. |
| `media_thumbnail` | Media service only. Generated by the thumbnail port after a clean scan. |
| `media_watermark` | Per-tree per-domain watermark advanced atomically with each media state change. |
| `media_reference` | Local copy of associations to members/events/albums. Fail-closed: a missing reference target keeps the association in `PENDING`. |

## Behaviour

### Upload lifecycle (10.1)

1. `createUploadIntent(treeId, mimeType, byteSize)` returns a signed
   exact-path `put` capability and reserves the `media_asset` row in
   `QUARANTINED` status with the SHA-256 the client committed to.
2. Browser uploads bytes directly to private quarantine using the
   exact-path capability.
3. `verifyUploaded(mediaId, sha256, byteSize)` re-checks the bytes and
   transitions to `SCANNING`. The verification reads the binary via
   the Blob Control Gateway, never via the public signed URL.
4. `scanAndPromote(mediaId)` calls the fail-closed scanner gateway. A
   `CLEAN` verdict generates the thumbnail, transitions to `READY`,
   publishes `MediaScanned` and `MediaAssociated` (for the owning
   album), and advances the watermark.
5. Any `FAILED`/`INFECTED` verdict moves the asset to `FAILED`,
   publishes `MediaQuarantined` with a `quarantinePath` already
   recorded for delayed cleanup.
6. `tombstone(mediaId)` keeps the binary path for the retention
   window, sets `status='TOMBSTONED'`, publishes `MediaDetached`, and
   schedules a delayed cleanup row.

### Blob Control Gateway (10.2)

- Lives in `services/media-service/.../adapter/out/blob/`.
- Issues exact-path signed `put` and `get` capabilities through the
  `BlobCapabilityIssuer` port.
- The signed URL is returned exactly once. It is never logged, never
  written to events, never persisted in domain tables.
- `invalidate(mediaId)` revokes subsequent capability reuse.
- The public REST surface only returns the `exactPath` plus the
  one-shot signed capability. Logged metadata is the media ID, the
  tree ID, and the MIME type only.

### Lifecycle, retention, cleanup, binary replication (10.3)

- `media_retention_hold` rows keep tombstones visible until the
  retention deadline. The delayed cleanup job (Task 10.5) reaps them
  in batches keyed by `retention_hold_until`.
- `media_binary_replication` records the canonical binary digest per
  source/target pair. Promotion requires the digests to match.

### Events (10.4)

- Topics: `media.events.v1`.
- Partition key: `treeId`.
- Payload contains: `treeId`, `mediaId`, `eventType`, `eventVersion`,
  `revision`, `occurredAt`, and event-type-specific allowlisted
  fields. No paths, no capabilities, no raw URLs.

### Migration and reconciliation (10.5)

- `MediaMigrationController` exposes `POST /api/v2/internal/media/migration/media`
  for idempotent loaders, plus `GET /api/v2/internal/media/migration/reconcile`
  for delta reads after a watermark.
- A local `media_watermark` table advances atomically with each
  mutation. Reconciliation reads `updated_at >= watermark`.

### Verification (10.6)

The verification gate (Task 17) drives real fault injection. Within
the service, the use cases enforce:

- scanner `FAILED` blocks promotion (fail-closed);
- a missing reference target keeps the association in `PENDING`;
- capability reuse after `invalidate()` raises `ForbiddenException`;
- delayed cleanup respects `retention_hold_until`.

## Configuration

- `familya.media.upload.max-byte-size` — 10 MiB cap (default 10485760).
- `familya.media.thumbnail.enabled` — toggles the real encoder path.
- `familya.scanner.fail-closed` — defaults to true; the placeholder
  vendor tag still fails closed.
- `familya.blob.vercel.store-id` — capability issuer HMAC scope.

## Acceptance

- `media_asset`, `album`, `media_quarantine`, `media_thumbnail`,
  `media_retention_hold`, `media_binary_replication`,
  `media_watermark`, `outbox_record`, `inbox_record`,
  `idempotency_record`, and `operation_audit` exist with the schema
  described here.
- Upload intent, verification, scan-and-promote, tombstone use cases
  exist and respect the fail-closed rules.
- `BlobControlController` returns a one-shot signed capability and
  the `BlobCapabilityIssuer` enforces HMAC scope and revocation.
- Migration controller exposes loader and reconciliation endpoints.
- All published events live on `media.events.v1`, partitioned by
  `treeId`, and contain no path or capability fields.
