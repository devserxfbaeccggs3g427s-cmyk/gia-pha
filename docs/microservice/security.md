# Security baseline

> Phase 6.4 deliverable. Per Requirement 13 (security baseline).

## mTLS

- All service-to-service calls run over mTLS using a local CA in
  `infra/ca/`.
- The CA is generated by `make ca` (wrapper for `tools/ca/make-ca.sh`).
- Each service gets its own leaf cert (24h TTL; rotated by
  `make ca-rotate SERVICE=<name>`).
- Service containers mount the CA into `/etc/giapha/ca/` and configure
  the JVM trust store via `-Djavax.net.ssl.trustStore=...`.

## Signed outbox

- Every outbox row is signed by the producing service's leaf cert.
- Consumers verify the signature before applying (Requirement 13).
- Signature algorithm: Ed25519 (chosen over RSA-2048 for size + speed).

## User-context JWT

- The gateway obtains a short-lived JWT (≤ 5 min) from `identity-service`
  after session validation.
- The JWT carries `userKey`, `roles`, `csrf`, `requestId`, and a
  signature.
- Downstream services verify the JWT and reject requests without one.

## Actuator gating

- `management.endpoint.health.show-details=when_authorized` — actuator
  details hidden from anonymous users.
- `management.endpoints.web.exposure.include` is per-service and only
  exposes `health,info,prometheus`.

## Secrets

- All secrets injected via environment variables (Requirement 13.2).
- `.env.example` carries placeholders only; `.env` is git-ignored.

## Service accounts

- Every service has its own MySQL user (Requirement 13.5). No shared
  service account credentials.
- MySQL user passwords read from env: `MYSQL_SVC_<NAME>` /
  `MYSQL_SVC_<NAME>_PASSWORD`.

## Known limitations

- mTLS uses a single CA; production should use intermediate CAs and
  per-environment roots.
- Outbox signing does not protect against replay; the idempotency-key
  registry in `audit-service` does that.
